# 选题方向思考

## 一、四步选题法

### 第 1 步：评分点反推

先明确评审到底看什么。海之子杯初赛是"线上评审"三大件，实际评审点可推断为：

- **真实性与专业深度**（申报书背景/场景是否懂行、是否用对标准）
- **可运行闭环**（Demo 是否真能跑出工程结果，而非 PPT 演示）
- **创新性**（技术方案是否有新意，是否只是套了个 ChatBot）
- **展示力**（视频 5 分钟内是否讲得清、看得懂、记得住）

选题必须同时服务以上四点——"真能跑出工程结果"优先于"演示效果好看"，但演示形式决定线上评审的第一印象。

### 第 2 步：交集定位

好选题 = 用户专业优势 ∩ 比赛赛道 ∩ 数据/算力/时间可行性 三者的交集。

本用户画像：土木工程大三（测量/结构/BIM 基础）、Python 可写项目、RTX 4060 8GB 本地推理可行、4 人 × 每天 2 小时 × 约 4 周。

### 第 3 步：差异化

- 选"有工程专业门槛"的细分场景——非土木团队做不了，降低被抄袭/撞题风险
- 用**中国标准（GB/T 51366-2019 等）**做护城河：评审里懂行的人会认可，外行做不出
- 避免只做"通用大模型问答"（无门槛、无创新）

### 第 4 步：验证清单（逐项打分，低于 3/5 的方向砍掉）

| 维度 | 检查问题 |
|---|---|
| 可行性 | 4 周内能跑出最小闭环吗？计算/数据从哪来？ |
| 新颖性 | 与公开产品/往届项目有何不同？ |
| 可演示性 | 3 分钟内能展示"输入→输出"全过程吗？ |
| 数据可得性 | 演示数据是否已有/能造/能脱敏？ |
| 团队匹配 | 4 人分工能否覆盖开发/文档/视频/答辩？ |

## 二、绿色建筑与可持续发展赛道 — 落地方向（本用户专项）

### 方向 A：建筑碳排放计算与评估助手（推荐度 ★★★★★）

- **场景**：从业人员（设计/造价/绿建咨询）输入建材用量、机电能耗等参数，智能体按 **GB/T 51366-2019** 自动完成建材生产/运输/建造/运行全周期碳排放计算，输出分项报告与降碳建议
- **核心能力**：碳排放计算引擎（可复用开源 GBT51366 项目的 39 个计算单元）+ Agent 对话编排 + 报告生成
- **为什么推荐**：标准明确（好验证）、数据易造（按标准输入）、工程门槛高（护城河）、"真能跑出工程结果"
- **风险**：计算引擎是核心工作量，须尽早锁定开源实现；注意许可证

### 方向 B：建筑能耗监测与节能优化智能体（推荐度 ★★★★）

- **场景**：面向公共建筑运维人员，接入电耗/空调/照明数据，智能体预测能耗、识别异常、给出节能建议
- **核心能力**：时序预测（Prophet/轻量模型）+ 异常检测 + 建议生成；可参考开源碳足迹计算器（AmberGreen）的 Prophet 预测 + LLM 建议架构
- **优势**：演示效果好（图表多、直观）；**风险**：真实能耗数据难拿（可用公开数据集或自造脱敏数据），预测精度难保证

### 方向 C：绿色建筑评估自动化智能体（推荐度 ★★★）

- **场景**：辅助绿建评审，智能体读取项目资料，对照绿建标准（如 GB/T 50378 或评价细则）自动核对得分项、生成评估初稿
- **核心能力**：RAG（标准文档问答）+ 资料解析 + 评估清单生成
- **优势**：RAG 技术成熟、文档类输入好演示；**风险**：评估结论的合规责任敏感，需定位为"辅助初筛"

### 推荐组合拳（A 为主、B 的图表为演示加分）

```
从业人员提问 → Agent 规划 → 调用计算引擎(GB/T 51366) 计算碳排 → 引用标准解释
→ 生成分项报告 + 降碳建议 → 可视化图表展示
```

技术栈建议（消费级硬件友好）：

| 组件 | 选型 | 理由 |
|---|---|---|
| 计算引擎 | 复用开源（如 GBT51366，MIT） | 4 周内自写 39 单元不现实 |
| Agent 编排 | LangGraph 或 Dify（本地部署） | Dify 出界面快、LangGraph 更可控 |
| 模型 | Ollama + Qwen2.5（7B 量级） | RTX 4060 8GB 可跑，答辩无网络风险 |
| 前端 | Gradio / Streamlit | 一天内出可交互原型 |
| 数据 | 自造脱敏样例 + 官方标准参数表 | 可控、可复现 |

## 三、通用避坑清单

- 选题过大（"智慧城市"级）→ 评审无法验证，砍到单场景单闭环
- 依赖评审环境没有的条件（GPU 集群、真实工地数据、企业 API）→ 必须本地可复现
- 创新点写成"用了大模型"→ 大模型是工具不是创新，创新在工程问题的解法
- 团队 4 人职责不清 → 队长（用户）先定 PM+架构，其余按"计算/Agent/前端/文档视频"分工
